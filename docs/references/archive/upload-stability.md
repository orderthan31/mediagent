# 동시 업로드와 큐 등록 안정성

동시 요청에서 보이던 `Job is busy`는 CPU/GPU 부족을 뜻하지 않는다. API가
공용 접수 잠금을 즉시 획득하지 못하면 409를 반환했고, 업로드 생성 요청에는
재시도가 없었다. 접수 중 전체 저장소 용량을 재계산하면 잠금 점유가 길어졌다.

## 처리 방식

- 업로드 생성·완료와 작업 접수의 최상위 공용 잠금은 최대 5초 기다린다.
  작업 실행 잠금은 기존 방식으로 유지해 GPU 작업을 순차 처리한다.
- 청크 수신은 비동기로 잠금을 기다린다. 대기 중에도 다른 요청을 처리하며,
  잠금 획득 후 업로드 위치를 확인해 같은 바이트의 중복 기록을 막는다.
- 잠금 충돌 응답에는 `code: job_busy`를 제공한다. 웹은 안전하게 반복 가능한
  요청만 같은 요청 ID로 최대 60초 예산 내에서 재시도한다. 요청 취소를 지원하며,
  파일 위치·리비전 등 일반 409 충돌은 자동 재시도하지 않는다.
- 최근 저장소 감사 결과가 있으면 기존 예약량·증가량을 보수적으로 반영하는
  용량 원장을 사용한다. 물리 디스크 여유 공간도 확인한다. 감사 결과가 없거나
  오래되면 전체 용량 검사로 돌아간다. 할당량 근처에서는 보수적 추정으로
  접수가 일찍 거절될 수 있다.

## 검증

`scripts/verify-concurrent-uploads.py`는 `VIDEO_STORAGE_ROOT=/tmp/stability-jobs`인
격리 API에서만 실행된다. 합성 영상 12개를 동시에 HTTP로 업로드하고, 업로드 생성,
완료, 작업 생성 요청을 반복해 중복 방지도 검사한다. 운영 데이터와 워커는 사용하지 않는다.

2026-09-29 Docker API 검증: 12건 모두 QUEUED, 중복 작업 0건, busy 오류 0건,
4.34초. 작은 합성 파일의 동시 접수 검증이며 대용량 전송·장시간 인코딩 부하 시험은 아니다.

디스크 부족, 네트워크 단절, 데스크톱 절전, Docker 중단은 별개의 장애 원인이다.
이번 변경은 일시적인 접수 경합을 흡수하며 실행 워커 수를 늘리지 않는다.
