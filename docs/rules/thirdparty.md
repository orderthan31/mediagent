# 외부 데이터 참조·반영 규칙

## Common

- 외부 데이터를 가져오기 전에 출처, 원본 위치와 해당 자료가 관리하는 범위를 확인한다. 정본이 지정된 주제는 그 원본을 우선 참조한다.
- 작업에 필요한 최신 범위를 직접 읽는다. 로컬 내보내기 파일이나 이전 조회 내용만으로 외부 원본의 현재 상태를 단정하지 않는다.
- 외부 자료의 확정안·제안·과거 이력과 실제 구현 상태를 구분한다. 가져온 자료를 곧바로 구현 승인으로 취급하지 않는다.
- 외부 원본을 갱신할 때는 최신 내용을 다시 확인하여 동시 편집을 보존하고, 필요한 범위만 수정한 뒤 다시 읽어 검증한다.
- 접근이나 검증에 실패하면 미확인·동기화 대기 상태를 명시한다. 오래된 로컬 자료로 원본을 덮어쓰거나 동기화 완료를 주장하지 않는다.
- 저장 위치, 정본의 중복 관리 방지와 원본 파일 ID 유지에는 [문서 관리 규칙](docs-manage.md)을 따른다. 외부 자료의 공유 범위와 이용 조건을 유지한다.

## Special

### 외부 기획과 공통 규칙

- 공통 규칙의 참조 원본은 `orderthan31/resort-survive`의 `docs/rules/`다. 채택한 Common은 그대로 유지하고 이 프로젝트에 의존하는 내용만 Special에 작성한다. 다른 프로젝트의 실행 권한·게임 기획·데이터·배포 경로는 가져오지 않는다.
- 기존 Notion의 사용자 결정은 전환 시 출처로 조회한다. 이후 개발 정본은 [문서 관리 규칙](docs-manage.md)에 따른 저장소 Markdown이며 독립된 이중 편집을 하지 않는다.

### 모델·스토리지·브로커

- 모델 등록/능력 선언과 실제 연결·추론 성공을 구분한다. 임의의 실모델/provider·과금 검증을 하지 않는다.
- S3-compatible 스토리지와 브로커는 공식 API·지원 버전·이용 조건을 확인한다. MinIO/RabbitMQ라는 후보 이름만으로 제품 선정·설치·운영 연결 완료를 주장하지 않는다.
- 외부 저장소 credentials·bucket/queue의 운영 데이터를 개발 fixture로 복사하지 않는다. 격리 테스트의 endpoint와 범위를 명시하고 서명 URL이나 비밀정보를 공개 문서에 싣지 않는다.
