# 문서 관리 규칙

## Common

### 문서 생성과 형식 선택

- 새 문서를 만들기 전에 기존 문서에 내용을 추가할 수 있는지 확인한다. 목적이 같은 문서를 작업마다 새로 만들지 않고, 독립된 목적이 있을 때 새 문서를 생성한다.
- 미확정 기획, 변경 가능성이 높은 요구사항, 기능 설계 초안, 기술 검토, 구현 계획, 작업 메모, 반복해서 참조하는 개발 컨텍스트, 코드와 함께 버전 관리할 내용은 저장소 내부 Markdown으로 관리한다.
- 새로운 기획과 설계는 Markdown으로 시작한다. 문서 형식이 명확하지 않은 경우에도 Markdown을 기본값으로 사용한다.
- Spreadsheet는 데이터 자체가 행과 열로 구성되어 있거나 정렬·필터·수식·집계가 필요한 구조화 데이터에 사용한다. 목록, 스탯, 스킬, 대사, 테스트 케이스, 일정, 상태 관리, 반복 데이터가 이에 해당한다.
- 기획 설명, 정책, 아키텍처, 개발 가이드, 회의 내용, 설계 배경, 장문 요구사항, 보고서를 표로 표현할 수 있다는 이유만으로 Spreadsheet에 넣지 않는다. Google Sheets를 기본 문서 형식으로 선택하지 않는다.
- Google Docs 등 문서형 외부 도구는 내용이 확정되었고 최종 기획서, 보고서, 제안서, 업무 설명서, 정책 문서 등을 장문으로 공유하거나 비개발자가 열람하는 데 이점이 있을 때 사용한다.
- 저장소 내부 Markdown으로 충분하면 외부 문서를 추가로 만들지 않는다.

### 문서 생명주기와 정본

- 아이디어와 논의를 Markdown에 정리하고 기획·구현 과정에서 갱신한다. 변경 가능성이 있는 동안 불필요하게 외부 문서로 이전하지 않는다.
- 내용 확정 후 개발 컨텍스트는 Markdown으로 유지하고, 구조화 데이터나 외부 공유 문서로 관리할 필요가 생겼을 때 적합한 도구로 이전한다. 확정되었다는 이유만으로 외부 문서로 이전하지 않는다.
- 주제별 정본을 명확히 지정한다. 같은 내용을 Markdown, Spreadsheet, 문서형 도구에서 독립적으로 중복 관리하거나 동시에 수정하지 않는다.
- 정본을 이전하면 기존 문서에는 필요한 경우 새 정본 링크만 남긴다. 다른 문서의 내용을 반복 복사하기보다 정본을 참조한다.

### Markdown 작성

- 새 Markdown 문서는 `docs/templates/` 아래에서 목적에 가장 적합한 템플릿을 사용한다.
- 일반 기획·설계 문서에는 문서 목적, 현재 상태, 주요 내용, 미확정 사항, 관련 문서를 포함한다. 전용 템플릿이 있는 문서는 해당 구성을 따른다.
- 불필요하게 긴 배경 설명과 반복을 줄이고 현재 결정과 미확정 사항을 구분한다. 사람이 읽고 개발 컨텍스트를 빠르게 파악할 수 있도록 작성한다.

### 참고자료 분류와 아카이브

- 참고자료는 `docs/references/` 아래에서 관리한다.
- `high/`: 중요한 참고문서.
- `midium/`: `high/`보다 덜 중요한 참고문서.
- `low/`: 중요하지는 않지만 가끔 필요한 참고문서.
- `archive/`: 이전에는 사용했지만 최신성이 떨어져 과거 이력을 확인할 때만 참조하는 문서. `high/`, `midium/`, `low/`에서 현행 참고자료로 쓰이지 않게 된 문서를 보관한다.
- `docs/references/`에 문서를 생성할 때는 중요도를 판단하여 반드시 `high/`, `midium/`, `low/` 중 하나에 배치한다. 아래 세션 간 인계용 `handoff.md`는 예외다.
- 새 파일을 생성할 때 기존 문서 중 대체되었거나 최신성을 잃어 아카이브할 문서가 있는지 확인하고, 해당 문서는 `archive/`로 이관한다.

### 세션 간 컨텍스트 인계

- 사용자가 인계를 요청하면 현재 작업 중인 내용을 `docs/references/handoff.md`에 작성한다. 인계 요청 없이 자동으로 생성하지 않는다.
- 작업 목적과 범위, 사용자 지시·확정 결정, 완료·진행 중·남은 작업, 관련 파일과 문서, 수행한 검증, 차단 사항과 다음 단계를 정리한다. 다음 세션이 작업을 이어갈 수 있을 만큼 구체적으로 작성한다.
- 다른 세션은 작업을 시작하거나 이어받기 전에 `docs/references/handoff.md`의 존재 여부를 확인하고, 파일이 있으면 먼저 읽어 현재 작업 맥락을 파악한다.
- 인계 내용을 읽고 확인하여 작업 맥락을 파악한 뒤 `handoff.md`를 삭제한다. 내용을 파악하기 전에는 삭제하지 않는다.
- `handoff.md`는 일회성 인계 문서이므로 중요도별 폴더에 분류하거나 아카이브·이력 사본을 만들지 않는다. 지속적으로 관리할 내용은 해당 정본 문서를 참조한다.

### 진행 계획 문서

- 진행 계획은 `docs/plans/` 아래에서 관리한다.
- `design.md`: 프로젝트의 디자인 철학과 시각 표현·UI/UX의 판단 기준을 관리한다. 확정된 방향을 유지하며 기능 목록이나 세부 구현 기획을 중복 작성하지 않는다.
- `specs.md`: 현재 확정된 프로젝트 컨셉과 제공하는 주요 기능의 정본 기획을 관리한다. 개별 수치, 세부 동작, 상세 구현 등 세부 기획은 작성하지 않는다. 주요 기획이 변경되면 현행 내용으로 갱신한다.
- `tasks.md`: 현재 실제로 구현해야 할 확정 태스크를 Markdown 체크리스트로 관리한다. 미확정 기획이나 브레인스토밍을 구현 태스크로 등록하지 않는다.
- `architect.md`: 현재 프로젝트의 거시적인 구조를 관리한다. Mermaid 등으로 쉽게 이해할 수 있게 표현하고 세부 구현 단위까지 쪼개지 않는다. 구조가 바뀌면 현행 내용으로 갱신한다.
- `ideation.md`: 아직 결정되지 않은 브레인스토밍과 기획을 정리한다. 구현 태스크로 확정되기 전까지 이 문서에서 관리한다.
- 현재 묶음의 모든 구현이 완료되고 새로운 기획이 요청되었을 때 `tasks.md`와 `ideation.md`를 초기화하고 새 내용으로 작성한다. 두 조건을 모두 충족하기 전에는 진행 중인 내용을 초기화하지 않는다.
- `docs/plans/` 문서는 아카이브하지 않는다.

### 규칙 문서 형식

- 모든 규칙 문서는 `Common`과 `Special` 영역을 구분한다.
- `Common`에는 다른 프로젝트에서도 적용할 수 있는 공통 규칙을 작성한다.
- `Special`에는 해당 프로젝트에 의존하는 규칙을 작성한다.
- 규칙 문서는 지정된 규칙 문서 템플릿을 기반으로 작성한다. 문서 관리 규칙 자체도 같은 형식을 따른다.
- 규칙 문서 템플릿은 [docs/templates/rule.md](../templates/rule.md)에서 관리한다.
- `docs/rules/` 하위의 모든 Markdown 문서는 `README.md`를 포함하여 위 템플릿을 기반으로 작성한다.

### Google Workspace 원본과 변경 이력

- 기존 Google Sheets·Google Docs 등의 수정 요청에서는 대상 문서를 식별한 뒤 동일한 파일 ID를 유지하여 원본을 갱신한다. 기존 문서 개선과 새 목적의 문서 생성을 구분한다.
- 변경 이력과 복구는 Google Workspace의 기본 버전 기록을 사용한다.
- 내용 추가, 구조 개선, 컬럼 변경, 스타일 수정 때문에 새 문서를 만들지 않는다. 단순 복구 목적으로 `backup`, `copy`, `v2`, `final` 등의 사본을 별도로 생성하지 않는다.
- 별도 문서는 사용자가 명시적으로 복사본을 요청한 경우, 기존 문서를 템플릿으로 새 목적의 문서를 만드는 경우, 원본 보존이 필요한 실험적·파괴적 변경을 수행하는 경우, 서로 독립적으로 유지할 문서로 분기하는 경우에만 생성한다.

## Special

### 저장소를 정본으로 관리

- 개발 기획·규칙·구조·현재 작업의 정본은 이 저장소의 Markdown이다. Notion에 같은 본문이나 회차별 검증 보고를 독립적으로 누적하지 않는다.
- 기존 Notion 기획·태스크는 이전 결정의 출처로 보존한다. 이 전환은 원격 페이지·DB를 삭제하거나 기존 결정을 폐기하는 작업이 아니다. 이후 현재 결정은 해당 Markdown 정본 하나에서 갱신한다.
- `docs/plans/`의 다섯 문서는 현재 내용을 제자리 갱신한다. 완료되지 않은 작업을 초기화하지 않으며 체크는 실제 구현·검증 완료에만 표시한다.
- `docs/references/high/`는 현행 개발·실행 계약, `midium/`은 보조 기술 조사, `low/`는 드문 참고, `archive/`는 구형 MVP·실험·과거 검증 기록에 사용한다. `midium` 철자는 공통 규칙의 경로를 그대로 따른다.
- 이전 문서는 현행 안내와 섞지 않는다. 보존 가치가 있는 과거 기록만 archive에서 참조하며, 중복·생성물·더 이상 쓰이지 않는 파일의 제거는 참조와 보존 대상을 먼저 확인한다. 문서 정리는 실제 미디어·자막·DB·설정·키·작업 WIP의 삭제를 포함하지 않는다.
- README는 제품과 현재 개발 진입점으로 유지한다. 과거 GPU·유료 호출의 성공을 현재 renewal 기능의 검증으로 재사용하지 않는다.
- 검증 원본 로그·스크린샷·비밀정보가 포함될 수 있는 운영 산출물은 저장소 밖에 보관한다. 현행 문서에는 필요한 결론·한계와 재현 방법만 기록한다. 작업마다 새 보고 문서를 만들지 않는다.
- 현재는 구현 중이며 정식 배포 버전·패치노트 발행을 수행하지 않는다. 향후 정식 배포 시 [배포 규칙](deploy.md)과 [버전 규칙](version.md)에 따라 실제 변경분만 기록한다.
